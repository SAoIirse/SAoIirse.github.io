Activity漏洞-1.0

发表于2026-10-20|更新于2026-10-21|Android
|浏览量:

Activity漏洞有很多种：Activity组件导出不当导致的信息泄露或拒绝服务，StrandHogg攻击（任务劫持），Intent重定向与混淆代理攻击，后台Activity启动滥用。在Android版本升级的过程中已经慢慢被修复一些，Android 9修复StrandHogg攻击；Android 12要求强制显式声明android:exported，适当避免了一些组件被泄露的问题；Android 4.2修改了Content Provider的默认导出行为。因此一部分漏洞几乎很少见了，本篇只介绍Activity组件导出导致的信息泄露或拒绝服务类型的漏洞。

相关知识回顾

Activity作为四大组件之一，负责用户交互，通俗的说就是一个页面就是一个Activity。我们需要知道Android 是用栈来管理 Activity，利用Intent传值，这里围绕Activity组件一起回顾。
首先是Activity组件的生命周期，类中定义了七个回调方法：

其次是Activty的启动模式：
standard模式：默认模式每次启动新建实例压栈
singleTop：栈顶复用模式，如果要启动的Activity在栈顶存在，则调用onNewIntent()方法。
singleTask：栈内复用模式，activity只会在任务栈里面存在一个实例。
singleInstance：单一实例模式，整个手机操作系统里面只有一个实例存在。
最后还有传值机制：
无论是各个Activity之间交互还是与其他组件之间交互都是由Intent完成。Intent是一个可序列化的数据结构，一般用于启动Activity、Service、发送广播。分为显示和隐式。

越权绕过漏洞

Activity越权漏洞的本质是，把需要限制权限访问的页面暴露在了外面；攻击方式为直接从外部调用Activity，进入到被暴露的页面。

主要特征：

  1. 隐式导出：有intent-filter标签但没有写明确的android:exported=”false”默认允许被外部应用启动

    2.显式导出：声明android:exported=”true”

    3.若在隐式或显式导出的基础上有android:permission保护，那么只有持有相应权限的应用能够启动，可能存在漏洞威胁

样本漏洞复现：

先运行一下sieve.apk看看是什么东西；目前来看首先有登录页面进去之后可以创建保存密码

攻击

审计AndroiManifest.xml中的声明，发现：
com.mwr.example.sieve.FileSelectActivity：
定义标签属性android:exported=”true”，显示导出

com.mwr.example.sieve.MainLoginActivity:
带有标签但未被声明android:exported=”false”默认为能够被访问,隐式导出

com.mwr.example.sieve.PWList：
从名字分析是密码列表页面，应该是登录后才能看到的敏感信息页面；这里声明android:exported=”true”，显示导出

现在通过审计AndroiManifest.xml文件，我们发现有三个包存在泄露风险，不过体是否涉及越权就要仔细看看这个包的作用了。拉起模拟器的真机设备，用drozer工具验证一下：
执行 run app.package.list 【枚举设备已安装应用包】

执行 run app.package.attacksurface com.mwr.example.sieve【利用drozer的攻击模块扫描目标应用com.mwr.example.sieve

执行 run app.activity.info -a com.mwr.example.sieve 【利用drozer用于获取Activity信息的模块，列出目标应用所有已导出的 Activity，并显示与它们交互所需的权限】

执行 adb shell am start -n com.mwr.example.sieve/.PWList 实现越权跳转

其余两个包也尝试攻击实现跳转，FileSelectActivity跳转进入文件目录，MainLoginActivity即为登录界面。因此危害最大的应为PWList和FileSelectActivity。

修复思路：修改AndroiManifest.xml文件中声明标签，android:exported=”true”，防止外部应用直接调用组件。

拒绝服务漏洞

此拒绝服务非彼拒绝服务，这里指的是拒绝本地服务，也就是APP被攻击后遭到了破坏，应用出现卡死或者闪退等。

漏洞原理：

攻击者向一个导出的Activity组件发送精心构造的畸形的、空的或恶意Intent数据，而该 Activity在onCreate()或onStart()等生命周期回调中通过getIntent()获取数据时，如果没有做空值判断、类型检查或异常捕获，就会导致应用抛出未捕获异常并崩溃。

漏洞触发条件：

1.组件可被外部访问（导出，或导出且有权限但攻击者持有该权限）
2.代码对 Intent 数据未做空值/类型/边界校验，且未捕获异常
常见数据类型
1.空数据或Action:
程序直接调用 getAction()或对Extra数据取值后立即使用，没有判断是否为null。攻击者发送一个不携带 Action或特定Extra的Intent，就会触发NullPointerException。
2.类型转换异常:
组件使用getSerializableExtra()获取数据后，直接强制转换成预期类型。如果攻击者传入一个不同类型或伪造类型的Serializable对象，就会触发ClassCastException。
3.无法反序列化的类对象:
攻击者传入一个自定义的序列化对象，但目标应用中并不存在该类的定义。组件在尝试反序列化时，会抛出 ClassNotFoundException导致崩溃。
4.数组越界数据:
组件通过 getIntegerArrayListExtra() 等方法获取数组后，直接按固定索引访问元素，而未检查数组的实际大小。传入空数组或元素不足的数组就会触发 IndexOutOfBoundsException。

样本漏洞复现

如上审计AndroiManifest.xml代码结果，三个组件存在被泄露风险。现明确查找拒绝服务漏洞，已知漏洞原理在于数据传输异常无法处理，取巧搜索getIntent和getStringExtra方法，最终发现OnCreate事件中出现，数据传输且未检测空值异常语句

也就是getIntent().getStringExtra(“com.mwr.example.sieve.PIN”).length()作为漏洞点

攻击

构造payload造成程序崩溃，强制退出：

payload构造思路：
1.由于MainLoginActivity可直接被外部调用，因此构造命令“am start -n com.mwr.example.sieve/com.mwr.example.sieve.MainLoginActivity”通过adb向MainLoginActivity直接传递Intent
2.构造“–es com.mwr.example.sieve.DOS 1”以String类型放入Extra：Key = DOS，Value = “1”
3.无“–es com.mwr.example.sieve.PIN”，向com.mwr.example.sieve.PIN传递一个空值，使.length()抛出异常。
tips:不过验证漏洞前需要执行 adb shell am force-stop com.mwr.example.sieve 避免由于MainLoginActivity的启动模式二次攻击时无法稳定执行onCreate造成应用崩溃

最终程序闪退，漏洞得到验证。

修复

该样本漏洞最简单的修复思路即，对Intent的值进行边界校验即可防护；当然如果加上try-catch异常处理机制做处理更好

防护后再次攻击验证，命令执行成功但应用程序已经不会强制退出，且调出日志查看明确本次攻击应用未崩溃，说明最起码防住了我们自己之前的payload^^。
