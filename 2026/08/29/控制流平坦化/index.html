OLLVM -- 控制流平坦化篇

发表于2026-08-29|更新于2026-09-02|CTF
|浏览量:

控制流平坦化就是在增加逻辑分析的负担，把原先简略的代码放到switch-case或者if-else的石山代码逻辑中。目的就是增加你分析的难度

核心原理：

把原本有自己顺序的基本块打乱然后插入一个主分发器进行调用实现原本的程序逻辑，加入控制流平坦化的程序每执行一步都要返回给主分发器，由主分发器判断并执行下一步走哪个基本块

认识一下模块名称

一张很经典的图：

序言 ：函数的入口。初始化状态变量
主分发器 (Main Dispatcher)
通常是一个巨大的while(true) 循环，内部包裹switch(state)。读取状态值决定下一步走哪去
子分发器 (Sub-Dispatcher) (变种)
更复杂的 FLA 会嵌套多层 switch，或者使用数学公式计算跳转目标，进一步隐藏状态转移关系。
真实块 (Relevant Blocks)：包含原始业务逻辑的代码块。它们不再直接跳转到下一个真实块，而是被“隔离”成了 switch 的一个个 case。
预处理块 (Predispatcher) / 状态更新
每个真实块执行完后，先通过更新state 变量，然后无条件跳转回主分发器，再由分发器在下一轮循环中根据新状态进行决定程序下一步怎么进行
返回块 (Return)：函数的出口，当状态变量达到特定值时，跳出循环并返回。

🐍 控制流平坦化执行流程 🐍

执行流程演示

1. 初始化

  • 序言设置 state = 1

2. 分发

  • 主分发器检查 state，跳转到 case 1（真实块 A）

3. 执行与更新

  • 真实块 A 执行业务逻辑，并在末尾将 state 更新为 2

4. 回环

  • 跳转回主分发器

5. 再分发

  • 主分发器检查 state（此时为 2），跳转到 case 2（真实块 B）

6. 循环往复……

  • 直到 state 变为结束标志

这就是控制流平坦化的核心机制：用一个状态变量驱动所有基本块的执行顺序，原有的分支跳转逻辑被打散，使逆向分析难度大幅提升。

对抗及还原：目标是重建真实块之间的直接跳转关系

使用 IDA 插件 D-810

D-810是一个基于IDA Microcode实现的可拓展的ida去混淆插件

反混淆原理：

其实这个插件的运行原理和混淆时进行的原理一样，都是对这个函数进行中间文件的编译。D810将目标函数的汇编指令，通过IDA的微码，动态翻译并构建成内存中的LLVM IR表示。然后再根据选定的反混淆方法文件进行加载，执行符号执行，追踪状态变量，然后重连基本块，把扁平化的状态机彻底拆解掉。将优化后的LLVM IR，反向生成回IDA的微码。之后IDA基于这份新的微码，重新生成该平台的汇编指令，并直接替换掉函数原来的汇编代码。

利用deflat执行：

把am_graph.py 与deflat.py放在同一目录下

执行原理：

识别组件：自动找到序言，分发器，真实块和预处理块
符号执行：从每个真实块开始，符号执行到分发器，求出state的值和对应目标块
二进制修补：直接修改elf/pe文件，将真实块末尾指令修改成直接连接目标块并且nop相关跳转回分发器指令

angr还原：

  1. 静态判断模块：就是认清楚主分发器，预处理器，子分发器，真实块等
  2. 利用符号执行恢复真实块的前后关系，重建控制流
  3. 根据第二步重建的控制流Patch程序，输出恢复后的可执行文件
